CI EVIDENCE (gh run view 45176914921 --log-failed):
- ubuntu: [manifest] DRIFT with 5 CHANGED: (1) BinaryResolverTest#realPosixFilesystemRequiresExecutePermission baseline=skip 'got: <false>...' -> run=pass (POSIX runner runs it - EXACTLY the machine-dependence T-208's AC2 finding predicted); (2) GitLocatorTest#windowsFallbacks... baseline=pass -> run=skip; (3) GitWorktreeManagerTest#forceRemove... baseline=pass -> run=skip 'Windows CWD-lock semantics required'; (4) LintAndFormatToolsTest#cppcheckDetects... baseline=pass -> run=skip 'cppcheck not present on this machine'; (5) ToolchainRegistryTest#clang64... baseline=skip -> run differs.
- windows: [manifest] DRIFT with 1+ CHANGED: LintAndFormatToolsTest#cppcheckDetects... baseline=pass -> run=skip 'cppcheck install is broken on this machine (library cfg failed to load)'.
- The build step then exits 1 (##[error]Process completed with exit code 1) - and the SAME failure would block EVERY future push, so this gates the whole pipeline.

ROOT CAUSE (design gap, not data): discovery/IDS are env-independent (all tests compiled from src/main/java), so the id set is a sound cross-env coverage contract; but pass<->skip STATES and env-flavored skip REASONS are environment facts. The gate treats any state/reason difference as DRIFT (exit 1), which can never be stable across dev/ubuntu/windows.

WHY NOT REBASELINE: no single environment's states match the others (dev differs from ubuntu AND windows; ubuntu differs from windows) - a rebaseline just moves the red. The states must become env-tolerant, not re-captured.
