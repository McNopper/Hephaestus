OWNER RULES (2026-11-20, chat, verbatim, in order):
1. 'if something gets into the v stage process, it is per definition not in a backlog anymore, only requirements can be in a backlog.'
2. 'a sprint-backlog we do not need... the ticker agent gets active, it looks at the available tickets and then they are processed. remove this.'
3. 'a backlog does not exist either. when i am chatting with the agent, the ticket is created in the system, ready to be processed. if the requirement is not complete, this is the case, where stage 0 escalates to the human.'
4. 'by ticking the v stages and a stage creates a ticket for the next stage, everything is pumped through automatically.'
5. 'another state, not-implemented... it is also a done state... the feature is not implemented, however, the task is "done"' + 'not_implemented can always happen, when it is decided not to implement'.
6. 'ready, which is a fresh ticket created no agent has taken yet care about'
7. 'ready -> in_progress -> in_review -> done is the normal case'
8. 'paused is the state, when the ticket can be further processed, when a dependent ticket is done'
9. 'blocked if a ticker can not be further processes. this is important, as this can create a chain. e.g. when an implementtation can not be done because some information is blocked, the whole ticket chain goes back to the requirement, which is then blocked as well.'

THE FINAL MODEL - SEVEN STATES, NO BACKLOGS:
- ready: fresh, unclaimed, unassigned - processable NOW. BIRTH state when there is no open dependency (no basis, or basis done).
- paused: the dependency wait (rule 8) - the ticket CAN be further processed once a dependent ticket is done. Birth state when the basis exists and is not done (readiness WAIT_UPSTREAM at birth); the moment the basis completes, the pump auto-resumes it paused -> ready (rule 4: everything pumped automatically). Never claimed directly - only the resume path (or a human status update) moves it to ready.
- in-progress: an agent holds it. claim: ready + unassigned + role/stage match + readiness READY -> in-progress + assignee (THE serialization point); task_release returns in-progress -> ready (assignee cleared).
- in-review: verify handed off; engine review is the only accept authority.
- done: built + verified; the ONLY divide state - a stage's completion creates the next stage's ticket (born ready, or paused if ITS basis is open) - the pump (rule 4).
- not-implemented: a DONE state (rules 5) - task complete, feature deliberately not built (retired/wontfix/upstream-never-adopted). CAN ALWAYS HAPPEN FROM ANY NON-TERMINAL STATE when the decision is made (ready/in-progress/in-review/blocked/paused), and the accept step can also land here instead of done. Terminal: readiness NOT_APPLICABLE, never claimable, NEVER DIVIDES (nothing built to verify).
- blocked: the hard stop (rule 9) - the ticket CANNOT be further processed (missing information/decision; stage 0 uses it to escalate an incomplete requirement to the HUMAN, never a pool). BLOCKING PROPAGATES UP THE BASIS CHAIN transitively to the requirement: implementation blocked -> design -> architecture -> system -> requirements all blocked, each hop recording the origin ('blocked by <downstream> <id>'). Clearing propagates DOWN the same chain: each ticket returns to its pre-block state (resume_to captured at block time; fallback ready).
- paused vs blocked: paused = mechanical dependency wait that self-heals when the dependent ticket is done; blocked = hard stop needing outside resolution, with chain escalation.
