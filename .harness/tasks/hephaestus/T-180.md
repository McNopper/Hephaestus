Owner requirement (2026-11-18, chat): "as the chat was split, i am using this one now. eclipse should also use this chat, that we have one ground of truth." The split mechanism: ChatView resumes ChatViewSettings.lastSessionId (Eclipse-side memory) while the human drives the live thread from the TUI - each surface resumes its OWN thread and the conversations diverge. Sessions are global per user on the shared v2 service, so the fix is resolution order: on open, the chat lands on the MOST RECENTLY ACTIVE session of the current project directory (GET /session scoped, newest time.updated first) - whichever client wrote it - then falls back to the remembered id, then to a new session. Manual choices (session switcher CP-05, "Open in Chat") keep working for the window lifetime.
