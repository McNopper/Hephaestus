Owner directive 2026-11-17: 'we need a guard, that we are launching not too much.' Root cause being guarded (evidence from the Eclipse start-failure investigation): 3 concurrent full-reactor `build.ps1 verify` runs (fleet reviewers/reworks, logs t075-verify 15:41:54 / t075-verify-full 15:44:11 / t059-verify 15:47:59) on top of an idle 28.1 GB / 38.9 GB commit charge pushed the machine past its limit and the Eclipse launcher failed with 'Failed to create the Java Virtual Machine' (0 hs_err, 0 WER records - launcher refusal, not a crash; eclipse.ini untouched since 08:52 and proven good by 4 successful starts).

Design - one choke point, `eclipse/build.ps1` (every fleet worker, reviewer, pre-push and CI invocation already goes through it):
1. EXCLUSIVE BUILD SLOTS: before invoking mvnw, acquire a build slot - at most BUILD_GUARD_MAX (default 1) concurrent reactor build. Handle-based lock files `build-N.lock` in `<git-common-dir>/build-guard/` (shared with worktrees via --git-common-dir; never inside target/ - `clean` would eat them; FileShare.Read so waiters can dump WHO holds a slot; the OS releases the handle if a build dies, so no stale locks). Bounded wait BUILD_GUARD_WAIT_SEC (default 1800, poll 10s) -> on timeout fail fast naming every holder + the BUILD_GUARD_SKIP=1 escape.
2. COMMIT-HEADROOM FLOOR: with the slot held, require >= BUILD_GUARD_MIN_MB (default 6144) free commit charge (Windows: Win32_PerfRawData_PerfOS_Memory; Linux: /proc/meminfo MemAvailable; unknown OS -> floor skipped with a log line), waiting within the same deadline, else release + fail fast.
3. BUILD_GUARD_SKIP=1 bypasses everything (emergency only).

The ticker's spawn cap (4 subagents) stays as is - it counts agents, not memory; this guard counts actual reactor launches, which is what exhausted commit charge.
