Owner question 2026-11-14: should store functionality move to SQLite ('more reliable')? Settled in chat: keep Markdown+git. Grounds: (1) links (basis/epic) and states are declarative file fields - the graph is recomputed deterministically from the file set on every query, no cached state to corrupt; (2) writes go through task_* verbs whose invariants live in the engine (parseable files, history events, done-time guard, blocked-state rules), task_doctor lints hand-drift - every reliability incident on record (B-027) was transport-level, not storage-level; (3) a binary DB breaks the git-native properties the design depends on: diff/blame review of tickets, PR-visible store changes, and the peer sync (commit->pull-rebase->push over the store subtree) - a SQLite file cannot be merged or rebased; (4) D-005 thinness: git already provides durable versioning - never rebuild what the platform provides. If indexing at scale is ever wanted: SQLite only as a rebuildable cache over the files, never as the source of record.
