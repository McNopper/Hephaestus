## Description

Operational finding (system ticker + chat session, 2026-11-14, three occurrences in opencode.log): the tasks stdio MCP server (`eclipse/tasks-tools.ps1` launcher) resolves jars from the reactor `target/` dirs — every `build.ps1 verify` wipes/rebuilds them, killing the server (exit code 1 after 17–52 min) for every live session using it. Sessions that hit the death get **no `task_*` tools for the rest of their life** (the tools vanish from the catalog; no runtime reconnect: `POST /api/experimental/mcp/tasks/connect` returns 404).

Observed consequences: stage tickers went BLOCKED mid-arc (honest NEEDS-HUMAN report — correct behavior); the chat session lost store access repeatedly; store registrations queued and lagged behind the work.

## Evidence

- `opencode.log` 2026-11-14: three exit-code-1 entries for the tasks server
- ticker-system's tick 4 BLOCKED report on U-111 (the arc had to pause)
- the chat session's `Unknown tool 'tasks.task_create'` errors during the same window

## Fix direction (owner decides)

- **(a) launcher-side (recommended):** the launcher prefers STABLE jars (the deployed dropins at `C:\eclipse-cpp\dropins\opencode-ide\plugins`) over the volatile reactor targets, falling back to targets only when dropins are absent — gates then never kill live servers
- **(b) upstream feature request:** a runtime MCP reconnect endpoint for local stdio servers
- **(c) documented accepted mode:** "expect store loss during gates — sessions re-arm at next start"

## Acceptance criteria

- A `build.ps1 verify` run does NOT kill a live tasks stdio server serving another session (proven by a store read before and after a gate from a second session)
- The launcher jar-resolution order is documented in `tasks-tools.ps1` and the tasks docs
- If the fix is launcher-side: the same launcher serves both gate rebuilds and live sessions without flapping
