Discovered in the 2026-10-29 alignment review: task_create was called with blocked=true + blocker text (creating U-103, the schedules-evaluation ticket sequenced after U-037) and returned SUCCESS - but the ticket sat in product-backlog with blocked=false and blocker=null. The blocked state had to be applied afterwards by hand via task_set_blocked (the proper tool, so the live state is correct; this ticket is about the API defect). Silently accepting-and-ignoring arguments violates least surprise AND has governance impact: a calling agent believes a ticket is blocked when it is not, so the pump will not park for it and NEEDS-HUMAN accounting is wrong. Fix in the tasks bundle create path: task_create either HONORS blocked/blocker (create, then apply the blocked state in the same operation with a history event recording the blocker) or REJECTS the request loudly with a validation error naming the ignored keys. Chosen behavior: honor - it matches caller intent and needs no second call.
