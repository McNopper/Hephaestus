Owner observation 2026-10-07: 'from the feeling, it seems a TUI is more responsive than our Eclipse harness - make an investigation what this could be.' Evidence before theory: MEASURE, then rank the causes.

Static seed (inventory done 2026-10-07, chat-session): zero Display.syncExec (UI marshalling is all asyncExec, ~86 sites across bundles - async avoids stalls but may flood/coalesce badly); TaskStoreWatcher has a 2s poll fallback under its watch service; the chat controller form-polls while a reply is in flight (U-014) and the late-reply watcher polls every 5s (CHAT_LATE_REPLY_POLL_MS); ChatPage/MarkdownPage probe page-readiness at 3s/8s; the Board refreshes through RefreshGate rate limiting; the TUI and Eclipse both attach to the SAME opencode v2 service, so the delta is transport + rendering + Eclipse overhead.

Probe plan: (1) UI heartbeat - a Display.timerExec(50) drift meter while interacting: measures real event-loop lag p50/p95 (this is 'responsiveness' as felt); (2) event-delivery delta - timestamp the same /api/event at the TUI subscriber and at the Eclipse handler, compare; (3) JFR during a normal work session (-XX:StartFlightRecording) - main-thread run queue, GC pauses, SWT paint/layout counts; (4) count asyncExec per inbound event (coalescing opportunity) and per-refresh re-layout size; (5) transcript path: how a chat message travels service -> controller -> StyledText (append cost of a large transcript).
