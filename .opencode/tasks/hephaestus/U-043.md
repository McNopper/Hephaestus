User direction 2026-09-20: "blocked belongs to the category like in-progress, in-review and so on - blocked is just another state a ticket can fall into." Today the store models blocked as an ORTHOGONAL FLAG (blocked:bool + blocker:str) layered over the five statuses (documented in the AGENTS.md state diagram). Change the model: blocked becomes a VALUE of the ticket status set. Semantics: a ticket falls INTO blocked from any active state (the prior state is remembered - a blocked_from field or derived from history); entering blocked requires the blocker reason; resolving (the NEEDS-HUMAN path) returns the ticket to the state it fell from; product-backlog and done are unaffected. Consumers, one model everywhere: store schema + TaskStore + TicketMarkdown (back-compat read of blocked:bool files), task_* tools (task_set_blocked/task_clear_blocked become status transitions; the blocked filter maps to the status), readiness (BLOCKED kind reads the status), fleet engine + waves NEEDS-HUMAN surface, Board (blocked renders as a peer state/column; the U-040 tree's blocked state icon reads the same source), docs (AGENTS.md state diagram, fleet-quickstart). Migration: existing blocked:true tickets are rewritten once (status: blocked, prior state + reason preserved); task_doctor validates the migrated set.
