Owner direction 2026-11-13/14, refining the previous wandering-V model. THE MODEL: (1) STATIONARY TICKETS - a ticket is born in its stage and never moves; the stage field is ownership, not a cursor. (2) THE PIPELINE IS THE LINK GRAPH - completing an upstream ticket CREATES AND LINKS the downstream stage's ticket(s) ('the ticket is divided further: design -> implementation'); epic links become the pipeline edges. (3) PER-STAGE TICKERS - upstream experimental.schedules (W1, adopted per the revised experimental policy; plain-timer fallback for older servers like U-100 did): one steward agent per stage ticks every X minutes, handles its OWN stage's tickets (new = READY, blocked, stale, finished) via readiness, works each goal-driven (U-105: finish this exact ticket, engine-owned verdict), and on completion divides + links downstream. SUBSTRATE ALREADY PRESENT: task_readiness computes READY/WAIT_UPSTREAM/STALE/BLOCKED from epic chains (H6); dispatch injects governing upstream definitions; claims are the only serialization point (concurrent tickers safe); budget admission caps inherited from the pump. RETIRES (adopt-and-remove): the wandering machinery - task_advance, task_pass_stage, task_report_horizontal as stage movement, the moving-cursor send_back (becomes rework: a failed downstream blocks/stales its upstream link). MIGRATES: V-enforcement from advance-time to done-time (definition ticket cannot close without artifact; acceptance = the chain's test tickets done). SCOPE WARNING: the movement verbs are woven through Board views, docs, skills and ~10 test suites - this is an architecture arc: architect-role design first (stage graph contract, migration path for live staged tickets, Board projection), then engine cut in chunks. Companions: U-105 (goal-driven fulfillment), U-037 (live acceptance of the autonomy loop).
