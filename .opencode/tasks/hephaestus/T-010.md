Reported live 2026-09-29: a reply generated while the user watched the Eclipse chat never appeared there. Evidence: workspace log (C:\Development\workspace-cpp\.metadata\.log) shows the send at 15:24:52, then ONLY the 2s form polls, then an assistant bubble with 68 chars at 15:25:24 and settle-time refreshes - while the server (ses_f37a21973ffeZeCwmRTC7KSOvY) holds the full 1415-char answer completed normally (finish=stop). Root cause: awaitReply's marker-less quiet-window path (TURN_QUIET_CONFIRM, 2s) fired at the boundary BETWEEN two tool calls - the narration step was completed (finish=tool-calls) and the first tool's part already terminal, so inFlightWork saw nothing in flight and the quiet window elapsed. A completed assistant step whose finish reason is tool-calls explicitly means the turn CONTINUES. Fix: Turns.replyEvidence rejects evidence whose finish is tool-calls/tool_calls (endedByCallingTool). Regression: interStepToolCallsMessageNeverSettlesTheTurn in HttpOpencodeClientComponentTest.
